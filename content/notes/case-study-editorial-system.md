# 조판 규칙을 코드로 강제한 지면

디자인 포트폴리오에서 자기 프로젝트가 약하게 읽히는 이유는 실력이 아니라 **제약이 없기 때문**입니다. 이 글은 그 약점을 "코드로 강제되는 규칙"으로 바꾼 기록입니다.

기간은 2026년 9월부터 11월까지, 결과물은 지금 이 지면과 그 아래의 디자인 시스템입니다.

![엔지니어링 감사 지면(/projects)](/case-study/study-projects.png)

## 1. 브리프 — 자체 발주임을 먼저 밝힌다

이 작업에는 클라이언트 브리프가 없습니다. 자체 발주입니다. 그래서 제약을 스스로 정하고, 그 제약을 코드로 강제했습니다.

목표는 세 가지였고, 각각 판정 기준을 먼저 정했습니다.

| 목표 | 판정 기준 |
| --- | --- |
| 기록이 오래 쌓여도 무너지지 않는 지면 | 새 글을 규칙 수정 없이 추가할 수 있는가 |
| 디자인 결정이 리뷰에서 검증되는 구조 | 취향 논쟁 대신 린트·빌드가 막는가 |
| 토큰이 코드와 디자인 도구에서 같은 값 | 값을 두 곳에서 따로 관리하지 않는가 |

## 2. 제약 — 전부 측정 가능하게

| 제약 | 이유 | 강제 수단 |
| --- | --- | --- |
| 색은 토큰만, 임의값 금지 | 다크모드·일관성 | ESLint `tailwindcss/no-arbitrary-value: error` |
| 악센트는 1도, 면적 10% 이내 | 지면이 장식에 먹히지 않게 | 팔레트 2종 분리 |
| 구조선 2px / 구분선 1px | 위계를 굵기로만 만든다 | 공용 `HairlineRule` |
| 타입 6단계 고정 | 새 값 발명 방지 | 단계표 외 값 미사용 |
| radius 4/6/8만 | 알약형 남용 방지 | 컴포넌트 기본값 |
| `dark:` prefix 금지 | 토큰이 모드를 전환 | 변수 참조만 허용 |
| UI는 `components/ui` 배럴만 | 디자인 시스템 우회 방지 | 직접 import 금지 |

이 표가 이 프로젝트의 결과물입니다. 화면이 아니라 **규칙이 결과물**입니다.

## 3. 결정과 버린 대안

**① 뉴스프린트(크림+잉크) 선택, 다크는 별도 팔레트로 분리**
긴 글을 읽는 지면이므로 종이 표면을 골랐습니다. 다크 팔레트는 제품 UI용으로 남기고 한 화면에서 섞지 않습니다.
버린 대안: 다크 단일 테마 — 장문 가독성과 인쇄 유사성이 모두 나빠집니다.

**② 세리프는 디스플레이 전용**
제목과 워드마크만 세리프. 본문에 세리프를 쓰면 장문에서 리듬이 무너집니다.
버린 대안: 전체 세리프 — 첫인상은 강하지만 3,000자에서 피로가 옵니다.

**③ 카드 대신 헤어라인**
목록을 카드 그림자로 나누면 지면이 대시보드가 됩니다. 구분은 1px 선과 여백으로만.
버린 대안: 카드 그리드 — 정보 밀도는 오르지만 신문 지면의 성격이 사라집니다.

**④ 숨겨둔 지면을 되살림**
`/projects`는 원래 `/about`으로 리다이렉트되는 빈 라우트였습니다. 증거를 숨기는 대신, 감사 기록과 게이트 다섯 개를 담은 지면으로 교체했습니다. 기존 규칙을 그대로 적용해 하루 만에 얹었습니다.

## 4. 프로세스

```
primitives / semantics JSON
        │  단방향
        ▼
CSS 변수 (--mds-*, 색 선언 194개)
        │
        ▼
Figma 변수 ── 같은 이름, 같은 값
```

- **에디토리얼 프리미티브 재사용**: 마스트헤드, 헤어라인, 드롭캡, 종결부호, 다단 조판
- **게이트**: `tsc --noEmit` → `eslint` → `next build`
- **새 지면도 같은 게이트를 통과해야 머지**: `/projects`는 정적 라우트로 생성됐고, 타입·린트·빌드 모두 통과했습니다.

## 5. 결과

| 지표 | 값 |
| --- | --- |
| 색 토큰 선언 | 194 |
| UI·에디토리얼 컴포넌트 | 12 |
| 콘텐츠 | 노트 14편 / 시리즈 4종 |
| 임의값 린트 | `error` (위반 0으로 통과) |
| `/projects` | 정적 라우트 생성, 라이브 200 |

## 6. 한계 — 숨기지 않는다

| 한계 | 영향 |
| --- | --- |
| 클라이언트 검증 없음 | "요구를 만족시켰다"는 증거는 아직 없다 |
| 인쇄물 실발주 이력 없음 | 조판 규칙은 있으나 도련·CMYK 실물 검증은 없다 |
| 접근성 감사 미실시 | 대비·키보드 점검은 부분적 |
| 규모 | 사용자 수가 아니라 구조의 완성도로 평가받아야 한다 |

## 7. 이 작업이 의미하는 것

1. **시스템을 만들고 강제할 수 있다** — 규칙을 문서로 두지 않고 린트·빌드로 막습니다.
2. **토큰을 두 곳에서 관리하지 않는다** — 디자인 도구와 코드가 같은 이름을 씁니다.
3. **새 지면을 하루에 얹는다** — 기존 규칙 위에서. 실제 사례가 `/projects`입니다.

규칙이 문서에만 있으면 지켜지지 않습니다. 코드가 막을 때만 지켜집니다.
